# Linux host TLS capture feasibility

Status: BLOCKED for an actual capture integration and positive end-to-end test. This is a design and test inventory, not evidence of implemented capture or universal coverage. The replacement MVP specification requires current signed capture authority before payload inspection and sanitization before observation queues, export, or persistence. The existing architecture says no queue contains raw values; delivery separately permits a bounded transient buffer for local extraction. A kernel perf or ring buffer carrying plaintext is a queued cross-boundary transport, not automatically an authorized transient extraction buffer. No exception is assumed here.

## Candidate and boundary

A candidate for a first *conditional* Linux experiment is a dynamically linked OpenSSL 3.x `libssl` process using HTTP/1.1 over TLS. Pin the exact Linux distribution, kernel, architecture, OpenSSL library build and symbols, application binary and linkage, TLS configuration and parser version in the fixture before making a compatibility claim. Hooks at `SSL_read`/`SSL_write` and, where used, `SSL_read_ex`/`SSL_write_ex` would require entry/return correlation and the actual successful byte count, including partial calls and errors. The read buffer is meaningful after successful return; a write must be accounted for by the returned count. Handle concurrent calls, process lifetime, library load/unload, object reuse, thread exit, process exit, and lost events; no ABI assumption is proof of correctness. These are candidates, not tested support. Statically linked, inlined, alternate TLS stacks, inaccessible processes, and kernel/ABI changes remain outside this candidate and must report a gap. No key harvesting or pinning bypass.

A compliant implementation must establish a reviewed execution boundary where current signed policy and the authorized workload assignment are checked *before* reading bytes, structural extraction and policy filtering finish before any queue/export, and raw buffers are bounded, short-lived and released on every failure, stop, expiry and revocation. In-kernel sanitization before transport is a possible research direction, not a demonstrated solution: stateful HTTP framing, fragmented traffic, compression, HTTP/2 multiplexing, bounded parsing and verifier constraints make it an unresolved design. Transporting raw bytes in perf/ring buffers and calling them transient would not resolve the explicit observation-queue boundary. A trusted in-process synchronous extractor could avoid that transport, but requires authorized instrumentation, a separate adapter and proof of its isolation, lifecycle and overhead; it is not black-box host eBPF. No production path is selected without resolving this boundary and review.

Bind source to authenticated collector assignment and a time-valid platform workload identity including host and process-start identity; PID alone can be reused and is insufficient. Keep source, instance, deployment, origin/destination references and capture provenance separate from operation identity. Enforce bounded inspection, callback time, parser work and memory; fail open for application traffic and report loss without sensitive labels. Policy changes must prevent subsequent inspection and purge noncompliant pending sanitized records. Do not add wire fields until compatibility and migration are approved.

TLS byte hooks alone do not prove inbound-to-outbound execution causality in opaque concurrent applications. Socket adjacency, time order, process and thread coincidence do not prove a parent. Where a separately authorized runtime hook or trustworthy propagated trace context is absent, represent the causal link as missing; incoming trace IDs are untrusted correlation, not identity or authorization. Even real fixture success cannot satisfy complete causality across arbitrary opaque systems or literal universal plaintext access.

## Evidence plan, not executed

A real positive fixture requires an approved Linux environment and instrumentation permissions, an exact pinned dynamically linked library/application, signed policy and assigned synthetic workload, local synthetic certificates and HTTP server/client, and an implementation that resolves the above boundary. Exercise a real TLS request and response with fragmented and partial reads/writes and synthetic secret values in headers, query and body; verify policy-permitted operation, structural names, direction, times, source and honest visibility through the common observation interface. Verify prohibited values are absent from all observation queues, export, logs, crash/support artifacts and temporary sinks. Prove attachment, detachment, switch and overlapping adapter behavior with an independently implemented real adapter. Record the exact environment and test result rather than inferring support from a TLS version.

Negative cases include invalid, expired or revoked policy before access; wrong or stale workload assignment and PID reuse; policy narrowing while work is pending; denied names and paths; malformed/fragmented messages, partial/error returns, process/library restart and missing symbols; overload and queue saturation with truthful loss; unsupported/static libraries; failed attachment; and stop/revocation races. Inspect relevant memory and artifacts for synthetic secrets within approved tooling. Separately test HTTP/2 multiplexing, HPACK, streaming, cancellation and loss against pinned real implementations before claiming those profiles. Capture timing, parser time, end-to-end latency, throughput and RSS against the existing targets on a recorded representative topology; no target is relaxed.

Execution environment inspected: macOS Darwin arm64; local OpenSSL reports 3.6.3, which is not evidence of a Linux fixture ABI. `docker` and `clang` commands exist; `bpftool` was not found on the host. No privileged probe, customer traffic, new dependency, or positive capture test was run. The unresolved privacy boundary and absent authorized Linux instrumentation mean positive and negative integration tests are NOT_RUN, not passes.

## Synchronous in-process interposition assessment

The explicit allowance in `03-privacy.md` for transient raw data inside the original process or bounded local parser memory makes a synchronous, in-process extraction design **potentially feasible** for an explicitly authorized dynamically linked Linux fixture. A reviewed `LD_PRELOAD` OpenSSL wrapper could call the real library and feed only the successful plaintext bytes into a bounded in-process HTTP parser and policy-filtered structural extractor, then place only sanitized records into a bounded export queue. This avoids a raw perf/ring transport. The allowance is not permission to inject into arbitrary customer processes, to spill raw bytes, or to treat a parser buffer as an unlimited queue. It does not establish that the latency, security or functionality requirements are met. `contour-core` currently exposes JSON extraction and checked record construction, not an HTTP stream parser, a capture lease or evidence of allocation-free callback behavior; the integration remains design work.

A viable implementation requires all of the following, validated against an exact pinned binary, loader, Linux kernel, CPU architecture and OpenSSL build:

- Establish authorized process and time-valid workload identity before attachment, verify the signed lease and relevant technique/service/operation permissions before inspecting payloads, and recheck a coherent current lease at each callback and before sanitized enqueue. Expiry, revocation, narrowing, stop, or uncertainty fail closed for capture and purge pending noncompliant data. Define synchronization so an in-flight callback cannot enqueue under a revoked lease; business calls must continue unaffected.
- Resolve the original symbol reliably with the exact ABI and symbol/version requirements; support `SSL_read`, `SSL_write`, `SSL_read_ex` and `SSL_write_ex` only when actually exercised. Preserve arguments, return values, `errno`, OpenSSL error-queue behavior, blocking semantics and application-owned buffers. Inspect read output only after success, and account for writes by actual successful count. Partial I/O, retries, zero returns, shutdown and errors must not invent bytes. Prevent duplicate capture if library entry points call one another.
- Use a per-thread recursion guard around symbol resolution, parser, allocator, diagnostics and export; nested calls bypass capture while still calling the real function, with truthful bounded loss accounting. Avoid unbounded locks and global initialization deadlocks, tolerate concurrent operations and callbacks, and establish ownership and lifecycle for SSL objects, connection state, process exit, thread exit, fork and object address reuse. Clean up bounded state without affecting TLS behavior. Secure initialization and handle unavailable original symbols safely without fabricating application results.
- Keep parsing synchronous, nonblocking, bounded and incremental. Apply operation/path policy before body inspection, limit inspection to the authorized per-message budget, and avoid retaining raw fragments beyond the smallest bounded parsing state. HTTP framing across TLS calls, concurrent use, pipelining and incomplete messages must be handled or explicitly dropped with truthful visibility. Sanitization must finish before any observation queue, IPC or export; no raw spool, diagnostic, trace, crash/support artifact or telemetry. A crash dump could include transient process memory, so the deployment needs an approved dump-handling boundary and secret inspection; do not promise guaranteed memory erasure.
- Never perform network, disk, policy refresh or blocking queue operations in the intercepted call. Bound allocations, state and CPU, drop on contention or saturation and maintain safe loss counts. Measure callback p99, request p99, throughput, cooperative parser time and process RSS against the existing targets with representative combined load, including TLS calls where no capture is permitted. These constraints are not verified merely by choosing synchronous extraction.
- Treat `LD_PRELOAD` as explicit launch-time instrumentation, not guaranteed host-wide black-box coverage. Static binaries, alternate libraries, direct/inlined calls, binaries that bypass interposable symbols, symbol/version mismatch, secure-execution loader restrictions and workloads started without the approved wrapper are uncovered. Detect the actual loaded library and attachment where possible, fail closed when evidence is absent, and surface an explicit coverage gap rather than a healthy zero. Do not bypass secure-execution restrictions or use privileged injection to extend reach.

The real-fixture plan must compare wrapped and unwrapped application-visible return values, errors, output and timing; deliberately exercise recursion, concurrent calls, partial I/O, lifecycle reuse, fork, lease races and saturated queues. Include an unsupported/static or secure-exec case showing explicit absence of coverage. Inspect all permitted sinks for synthetic secrets and exercise process memory/crash handling under an approved test policy. These tests are NOT_RUN. This alternative neither proves HTTP/2 support, causal links, nor universal black-box coverage, and does not resolve opaque-system barriers.
