# Proposal: source-bound instance attribution

Status: design for review, not an implemented attribution guarantee. This preserves the current batch wire format. It cannot establish a verified origin merely by joining a collector-supplied source ID to a row: trusted provisioning and capture-time source selection are essential. The replacement MVP still requires real evidence for each integration and access boundary.

## Existing boundary

`contour.sources` is immutable and keyed by `(tenant_id, source_id)`; its composite foreign key binds collector and deployment scope to an enrolled workload assignment. `source_authorization` supplies technique and parser profiles. Admission reads those rows after acquiring the collector advisory transaction lock and compares record workload fields and parser profile against them. Catalog observation windows retain `source_id` and the full workload-scoped source foreign key. These establish deployment-scoped enrollment, not workload instance identity or proof that a specific call originated there. The collector mTLS identity does not itself authenticate every observed workload.

The 500-source limits in authority refresh and `AdmissionInputs` bound a request/snapshot, not a demonstrated database-wide collector quota. A batch has at most 500 records; a long-lived collector can encounter more than 500 instance lifecycles over time. Historical retention and pagination must be designed, not assume 500 total sources.

## Proposed authoritative binding

Add an immutable `workload_instances` identity row with tenant, project, service, environment, deployment and issuer-assigned instance lifecycle UUID. A composite foreign key to deployments enforces scope; a unique key over the full scope and instance supports a precise binding FK. Store only a bounded, reviewed representation of platform identity and evidence reference if required; do not persist arbitrary platform labels or secrets. Trustworthy platform-specific enrollment must establish uniqueness and bind an actual lifecycle (for example, verified pod/container identity, or host identity plus process start), including issuer, access and revocation semantics. A fresh instance UUID is required on replacement/restart. Exact verification mechanisms are an unresolved integration decision.

Add immutable `source_instance_bindings` with `(tenant_id, source_id)` primary key, collector and full deployment scope, and instance ID. Its composite FK to the existing full source identity and composite FK to the instance row prevent cross-tenant and cross-deployment binding. Insertion and source creation occur atomically under the same collector lock by a trusted provisioner, with no UPDATE or DELETE, no reuse of source ID or nonce, and no later binding of pre-existing unbound sources. A collector observing multiple instances gets distinct sources; multiple collectors or approved capture points may bind distinct sources to the same instance. Source identity is not itself evidence of correct routing: the adapter must select the source from trusted process/container context at each capture and prevent cross-request and stale-context reuse. Reject or classify unknown when that cannot be established.

A source allocated to one lifecycle must never be reused for a successor, even if PID, IP or platform name is reused. The enrollment path must authenticate the provisioning authority and check that the specific collector is permitted to observe that lifecycle. Composite FKs establish relational scope, not platform authenticity, collector trust, or correct event attribution. No inference from trace headers, caller-provided instance fields, timing or socket proximity may upgrade an observation to verified origin.

## Time, authority and historical joins

Introduce a trusted, bounded lifecycle validity record and an append-only end/revocation event rather than editing the identity or rebinding a source. Define precise inclusive start / exclusive end semantics and authoritative platform clocks in the implementation review. Capture-time authority and instance lifecycle must cover the entire observation interval; a window spanning a lifecycle boundary cannot be assigned to one instance. Existing `first_seen` and `last_seen` are collector-provided timestamps: syntax and ordering are not proof of actual capture time. Establish a justified clock/skew and trusted capture mechanism per adapter; when unavailable, expose attribution as unknown rather than verified. Server receipt time alone cannot prove origin or capture time.

Allow late delivery only if trustworthy capture evidence places the complete window within the lifecycle and signed capture authority; separately recheck current collector policy and revocation at admission. New binding/end/revocation writes must take the same collector lock as admission, whose blocking lock statement precedes a fresh READ COMMITTED authority read and is held through inbox commit. Define cross-collector lifecycle closure locking order and test concurrent mutations; avoid a closure path that races admission on another collector. A lifecycle ended after capture does not automatically invalidate a properly evidenced earlier queued observation; current authorization and revocation rules still apply. Retain immutable binding and lifecycle evidence for at least as long as referenced observations and receipts; do not silently turn historical unknown into verified attribution.

Catalog reads may join a source binding only after the admission/evidence rules establish eligibility, and must communicate verified versus unknown explicitly. Existing unbound sources and records remain unknown. Never backfill from guessed labels or assign all old records when a new binding is created. Version any new public response separately and review downgrade behavior; do not alter the batch or authority wire by assumption. Worker processing after revocation must not manufacture verification from a binding alone; persist or deterministically retain the admitted evidence decision with the observation under a reviewed model.

## Roles, migration and access

Use forced tenant RLS and tenant-scoped composite keys for both tables. Only the trusted administrative provisioning path may insert identities and bindings, under the existing role and lock discipline; runtime, ingestion, worker and reader roles receive only the least SELECT required for their specific workflow, with explicit tenant RLS policies. Do not grant those roles writes, BYPASSRLS, or broader inbox/business privileges. Keep invoker-rights functions, fixed search paths and revoked PUBLIC privileges. SQL credential holders and provisioner remain trusted; tenant context is not independent authentication.

Apply an additive transactional migration with no synthetic instance backfill. Existing sources remain unbound permanently; new bound sources use a new ID. Check migration preconditions, forced-RLS behavior and rollback under the actual provisioning executor, and ensure older readers/writers continue to handle unbound sources. Plan schema version compatibility and rollback before deployment; immutable rows and retained references make destructive downgrade unsafe without an explicit data decision. Bound storage growth, lifecycle/end events and source history with retention and pagination without deleting referenced evidence. A separate design is needed for workloads lacking a trustworthy platform lifecycle identity.

## Required evidence before implementation is accepted

- Database constraints and real role tests: reject cross-tenant, cross-project, cross-deployment and wrong-collector bindings, updates, deletes, source/nonce reuse and unauthorized reads/writes; verify forced RLS and restricted logins.
- Admission and catalog integration: prove old sources remain unknown, no retroactive reclassification, instance-specific views preserve tenant authorization, and existing wire and lifecycle workflows remain compatible.
- Two concurrent instances plus restart with reused PID/IP/name: actual capture integration identifies each correctly; stale source and cross-request context cannot be used as successor identity. Negative controls include untrusted headers and ambiguous/opaque workload context.
- Time and race tests: bounded interval edges, skew, lifecycle-spanning windows, delayed queue delivery, revocation and policy expiry; concurrent admission versus binding/end/revocation across collectors, rollback and fresh-snapshot behavior. Demonstrate lock ordering and bounded waits.
- Capacity and privacy: more than 500 historical sources with bounded per-request batches and pagination; overload and retention behavior; inspect logs, queues and retained evidence for synthetic secrets. Tests must use real integration boundaries for verified claims, not only inserted rows or unit fixtures.
