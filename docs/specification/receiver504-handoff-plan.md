# Receiver 504: request-to-committed-root private handoff

Status: dormant implementation of the private root handoff, authenticated HTTP/1 IncomingMessage registrar, and versioned producer hook. The owned ephemeral host mTLS fixture covers the registrar and negative controls; hook tests use a model. The pinned Node-RED runtime, checked 504 loader/profile, deployment/issuer binding, SQL receiver enrollment, evidence transport and causal edges still require implementation and actual qualification. Profile 503 and its checked bytes remain immutable.

## Proposed private ABI, no wire changes

All four capabilities below are closed over by the checked 504 initializer; none are exposed to Node-RED messages, nodes, settings, headers, app code or a general `require` API. Opaque tickets are identity-only frozen empty objects held in private maps; their fields are never caller JSON, strings, or booleans. `WeakMap` lookup alone is not an authority check.

1. **Pre-app registration.** The 504 HTTPS handler checks its already authenticated actual socket and current locally installed enrollment/permit and intended backend leaf, validates the bounded closed gateway binding/digest, removes reserved carrier headers, then registers the exact `IncomingMessage` in a private `WeakMap<IncomingMessage, entry>`. Entry has one CSPRNG root, checked immutable binding/digest, local finite deadline and one-use state. It calls the Express handler once regardless of evidence availability; failure leaves no registration and never blocks forwarding on DB, disk or network. Permit/enrollment/connection identity are independently checked; header, cert alone or caller-created object is not authority. The private registrar is created and held only by the 504 startup closure, not exported as a general registration function. HTTP/2 remains unsupported by the existing dispatcher.
2. **Consume at existing inbound branch.** A 504-only private runtime method consumes through closure access while executing the checked `onSend` branch, after `atPoint` and scrubbing. Obtain `msg.req` via own data descriptor; reject proxy/accessor/replacement and require all messages in a batch to reference the same registered object. Consume exactly once, recheck permit/deadline and use the entry's root in both `ROOT_INTENT` and ALS. An unregistered or previously consumed request can follow ordinary behavior but creates no receiver evidence; no second root may stand in for this registration. Hold no strong reference to the request after consume. The documented pinned Node-RED HTTP-in/clone identity is source evidence only; actual 504 execution must prove it.
3. **Root enqueue ticket.** Add 504-only `prepare(bindingBytes)` to mint a CSPRNG root in a bounded opaque one-use registration, and `offerRoot(registration)` to create the root event and opaque ticket atomically only after the exact event is successfully appended under the existing `offer`/sequence/fits/gate rules; otherwise return a registered `dropped` result with the same prepared root and no ticket, recording the same loss as the existing producer. An unregistered request returns `undefined`; stale or aborted registered requests return `invalid`. Store `ticket -> {event identity, root, deadline}` privately alongside the event. The runtime separately continues its established context/business behavior on offer failure; it must never mistake `undefined`, a caller-supplied lookalike or `record()` success for a ticket. Recheck permit after enqueue; if it fails invalidate the ticket and evidence association without altering already admitted SQL20 facts. Avoid a second root offer. Attach provisional `{ticket,binding_digest,delivery_handle,receiver scope}` only to an initializer-owned bounded map.
4. **Freeze and settle.** At `freeze`, map the exact root tickets belonging to the frozen event prefix to that immutable `batchId`, `sha256`, and lossless epoch; later offers belong to later batches. Frozen retry must preserve those mappings. After the existing exporter validates the exact authenticated accepted/duplicate receipt and `ack` succeeds while `alive` and current authority still hold, an internal 504-only acknowledgement operation atomically consumes the frozen batch and transitions only its own mapped root tickets to committed. It returns an opaque, one-shot committed-root capability to the trusted receiver-outbox closure, not the public exporter result; identity/scope, exact root, binding digest, batch/epoch and original deadline remain privately attached. A mismatched/late/duplicate notification cannot settle a different batch, ticket, epoch, or session. Recheck gate and callback liveness at the commit boundary. `sendOnce`'s boolean alone must never trigger settlement.
5. **Receiver fact outbox.** Only a committed-root capability may atomically create one bounded immutable receiver fact matching the private registration's tenant, gateway/generation, handle, receiver runtime/epoch, root and binding digest. The fact is queued for a future separately authenticated evidence-client transport; SQL20 acceptance is necessary but not evidence-endpoint acceptance or a verified edge. Do not introduce an endpoint, SQL, service or grant in this source-only slice. On queue failure, expired authority, close, cancellation, unknown ACK, process restart or ticket invalidation, drop the association and record bounded loss; do not manufacture receiver success. A retried SQL20 batch with a verified `duplicate` receipt may settle the exact original frozen tickets once. A duplicate receipt or retry after settlement cannot enqueue a second fact. Authoritative SQL20 root lookup and receiver/gateway authorization remain mandatory in the future admission/reconciliation boundary.

## Bounds and failure semantics to preserve

`private-producer-runtime.js:17-20,37-46,63-67,161-170` bounds runtime pending/frames/dispatches to configured `maxPending` (504 candidate inherits 32) and TTL to 5 seconds in the existing launch. `private-handoff.js:12-17,20-29,36-46` validates batches 1..500 events, 512..1,048,576 bytes, configured queue 2*batch..268,435,456 bytes and TTL 1..86,400,000 ms; gate closes/clears on authority, oldest event, pending overflow, or reserved-attempt expiration. **Important:** in the inspected implementation `queueBytes` is validated at construction but is not otherwise used for an explicit aggregate byte counter; do not claim it enforces total queue storage. Actual event admission is limited by `fits` and `maxBatchEvents/maxBatchBytes`, with one frozen prefix and one reservation. 504 must account all provisional maps and outbox bytes explicitly under an approved aggregate ceiling without increasing any existing authority, batch, callback or queue deadline. Suggested conservative starting caps for review: at most 32 outstanding pre-app/association/outbox entries total, at most 32768 additional bytes total, each expires no later than the minimum of its original 5000 ms request ceiling, queue TTL and permit/enrollment deadline. These are proposed limits, not existing enforcement or a guarantee that evidence arrives in time. No unbounded timer, strong request-object retention, durable disk write or extra authority extension in a callback.

`pending` overflow materializes a loss event when capacity allows; a reserved attempt drops interleaved events into a loss range; u64 exhaustion is terminal for new offers. A false root offer must never leave a settlement association. `close()` and permit/loader invalidation clear pending, frozen and association state; cancellation must invalidate only its own ticket and never acknowledge an unrelated frozen batch. Transport timeout/unknown ACK leaves frozen retry semantics intact only while the original gate/TTL permits, and must not release a receiver fact. Never delay business forwarding or wait for SQL/network inside the request/hook callback.

## Initial dormant foundation

`collectors/nodered/receiver-integration/private-root-handoff.js` is a source-only initializer building block wrapping the existing private SQL20 handoff. It exposes separate root producer, exporter and outbox facades. Its initializer must retain exclusive ownership of the underlying base and pass the exporter facade directly to the existing private exporter; otherwise a caller with the raw base or direct access to `ack` could bypass the intended boundary. This is an in-process capability discipline, not authentication: any code able to require the module can create its own isolated object, which confers no global authority. The initializer must independently verify its receiver scope and create the base with the same tenant, runtime, epoch, permit and queue settings. The wrapper checks binding scope against the initializer-supplied scope but cannot inspect or authenticate the opaque base configuration.

The foundation mints each root internally from 16 CSPRNG bytes, checks active-root collision with at most four attempts, and never accepts a caller-chosen root. Durable SQL uniqueness remains mandatory. Prepared registrations count toward the same bounded capacity; live committed roots remain reserved until drain, cancel or expiry. The foundation associates root tickets with matching root events in the actual frozen canonical prefix, never uses JSON-parsed numeric sequence or epoch fields, and moves only matching tickets to drainable state after underlying `ack` succeeds. Cancelled/expired root identities retain a bounded tombstone until that exact prefix is acknowledged to prevent root reuse from attaching a new ticket to old evidence. At most 32 root identities and 32768 accounted association bytes are held; each ticket deadline is the minimum of 5000 ms, supplied queue TTL and authority deadline. Its outbox is an in-memory one-shot drain of a validated receiver-wire value, not a durable sender, endpoint, or committed receiver fact. A trusted future initializer must arrange cleanup and avoid passing `ack` to application code. No actual IncomingMessage registration, Node-RED hook, 504 loader/profile, authenticated evidence delivery, SQL admission, or edge is implemented here.
