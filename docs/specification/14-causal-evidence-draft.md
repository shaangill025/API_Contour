# Causal evidence protocol draft

Status: proposed; not an implemented endpoint, schema, admission rule, or grant. Review is required before implementation. Existing V2 capture and SQL20 producer envelopes remain unchanged. A receiving integration uses a new opt-in profile and does not reinterpret profile 503. Parsed data is untrusted; syntax alone confers no authority.

## Three facts and trust boundaries

A verified edge requires one committed authenticated producer dispatch attempt, one gateway-authenticated assertion binding that attempt to an exact committed REQUEST observation and its verified origin proof, and one durable one-use receiver assignment to a local root. All three must match in tenant, enrolled identities, generations, epochs and marker scope. Neither a marker, header, gateway request identifier, data codec, producer grant nor provisional receiver fact establishes the edge alone. Missing or inconsistent facts remain unresolved. Application forwarding and the original authority and stream ceilings remain independent of evidence reconciliation.

The managed gateway removes inbound reserved carrier headers, generates an unpredictable handle for every actual backend delivery, and authenticates the backend connection using a gateway-only mTLS identity. The opt-in receiver hook runs before application code, checks that authenticated connection and associates the handle with the actual request object in a private identity map. Consumption creates a local root and a provisional fact; it cannot be invoked by a fabricated request object, copied header, second consumption, or alternate backend identity. Enrollment and instance binding are separate from certificate possession. This trusted operator-controlled integration cannot defend against a privileged host or unrestricted same-process code. No synchronous database or remote key lookup is added to business callbacks.

## Proposed version 1 payloads

A pre-delivery binding and two separate authenticated endpoints, `POST /v1/causal-evidence/observer` and `POST /v1/causal-evidence/receiver`, are proposed; no endpoint exists. Each object is closed: all fields shown are required, unknown and duplicate keys are rejected, and no arrays are present. Binding input is limited to 2048 UTF-8 bytes; endpoint objects are limited to 4096 UTF-8 bytes. UUID means canonical lowercase 36-character UUID; id128 means exactly 32 lowercase hex characters; sha256 means exactly 64 lowercase hex characters. Epoch means a JSON string containing the canonical unsigned decimal representation 1..18446744073709551615, with no sign, whitespace or leading zero. A Node implementation must retain this string or use lossless BigInt parsing with explicit range checking; it must never convert through a JavaScript Number. The existing SQL20 envelope's numeric representation is unchanged; comparison requires exact lossless conversion. `wire_version` is the JSON integer 1.

Canonical JSON uses existing sorted-object `batch::canonical_encode` rules after strict typed decoding. Compute each SHA-256 over its UTF-8 domain followed by canonical bytes: `apicontour/causal-evidence/binding/1\n`, `apicontour/causal-evidence/observer/1\n`, or `apicontour/causal-evidence/receiver/1\n`. Decoders, decimal rules and canonical bytes require shared test vectors across runtimes; no codec is yet implemented.

### Binding available before backend delivery

The gateway allocates a frontend REQUEST `record_id` before forwarding and constructs this immutable binding from locally available data. The existing `Capture::begin` allocates a UUID before `finish`; using that same identity across the new handoff remains an implementation and race-condition proof obligation. No batch ID or proof ID is required at this stage.

| Field | Type | Meaning |
| --- | --- | --- |
| `wire_version` | integer, 1 | Binding version |
| `tenant_id` | UUID | Tenant claim, independently authenticated |
| `gateway_id` | UUID | Independently enrolled gateway identity |
| `gateway_generation` | id128 | Fresh generation assigned and bound by the enrollment/authority mechanism |
| `collector_id` | UUID | Enrolled capture collector |
| `record_id` | UUID | Preallocated frontend REQUEST record identifier |
| `producer_runtime_id` | UUID | Claimed producer runtime |
| `producer_session_epoch` | epoch | Claimed producer epoch |
| `producer_attempt_id` | id128 | Claimed producer attempt |
| `marker_digest` | sha256 | Claimed attempt marker digest |
| `receiver_runtime_id` | UUID | Intended enrolled receiver runtime |
| `receiver_session_epoch` | epoch | Intended receiver epoch |
| `delivery_handle` | id128 | CSPRNG-generated unique backend delivery handle |
| `retry_of` | id128 or null | Immediate prior backend delivery handle; null for first delivery |

Before minting the binding, routing must map the actual authenticated upstream receiver peer leaf and connection to the intended enrolled receiver and epoch, using locally available valid enrollment and pinned identity. A claimed target or a certificate alone is insufficient. If that mapping cannot be made without a network/database wait or is ambiguous, evidence is unresolved and ordinary business forwarding remains independent. Binding bytes and digest travel only on the authenticated, dedicated gateway-to-receiver channel and bind the actual registered request object. They are not bearer authority; producer fields remain claims until later verification. The enrollment mechanism below defines the issuer, generation, key rotation and leaf mapping; `gateway_generation` is not a self-issued grant.

A frontend REQUEST record ID may be shared by backend retries. Each actual delivery, including retry to another receiver, has a fresh handle and immutable binding reflecting that actual receiver. `retry_of` identifies the immediately preceding delivery within that same frontend request and gateway generation. Reconciliation requires an acyclic, same-request chain with consistent producer scope; an absent predecessor remains unresolved. Responses cannot substitute for the frontend REQUEST.

### Observer and receiver objects

The final observer object has exactly `wire_version` (integer 1), `binding` (the complete closed object above), `batch_id` (UUID), and `signed_marker` (the exact ASCII `ac1.` marker extracted from this same frontend REQUEST, 1..1024 bytes). It is emitted asynchronously after capture freezes and identifies the committed V2 batch; the binding already fixes `tenant_id`, `collector_id` and REQUEST `record_id`. Admission verifies the exact committed `(tenant_id, collector_id, batch_id, record_id)` V2 REQUEST and resolves its verified origin proof authoritatively. SQL17 `contour.origin_proofs` uses primary key `(tenant_id, proof_id)` and a unique `(tenant_id, collector_id, batch_id, record_id)` key. The regular ingestion receipt supplies batch and receipt IDs but not a proof UUID; the sender need not invent or predict one. The authoritative resolver must verify the exact unique mapping and proof, preserve its `proof_id` internally, and reject missing, conflicting, response or wrong-origin records. At observer admission the source REQUEST and its complete verified proof MUST already be committed; missing, incomplete or mismatched source/proof is rejected without storing a successful observer receipt. The gateway may retry after commit only while its current authority remains valid. Extract the marker from that exact REQUEST at the trusted gateway before reserved headers are stripped, reject missing, duplicated, malformed or ambiguous markers, and retain those exact bounded bytes with the request binding through the asynchronous outbox. Authenticate the gateway's statement that these were the bytes extracted from that request. Verify the marker signature and exact canonical encoding against the SQL23 key binding `(tenant_id, runtime_id, epoch)`, independently validate its generation/session and marker digest using the existing marker wire digest domain, and compare marker tenant, runtime, epoch, attempt and digest with the binding and committed producer attempt. Check marker root and activity against that attempt as well. The proof's actual downstream mTLS `leaf_sha256`, `credential_id`, `lifecycle_id` and `instance_id` must exactly match the SQL23 bound producer product credential, leaf, lifecycle and instance, and SQL18 runtime binding; proof `collector_id` and `source_id` must equal the gateway enrollment's capture mapping. The producer's SQL18 runtime collector/source is independently enrolled and authorized and may differ from that gateway capture collector/source: runtime authorization uses technique `runtime`, whereas the gateway mapping uses technique `gateway`. Never require those integration identifiers to be equal. Correlate the exact tenant, originating project/service/environment/deployment, product instance, lifecycle, credential and peer leaf against the producer binding and signed marker; independently check each integration's current source authority. This supports interchangeable capture without treating a capture integration's identity as the originating product identity. A valid signed marker paired with another peer leaf, lifecycle, instance, source or request is rejected. SQL23 key binding itself proves neither signature possession nor TLS identity; all checks are mandatory.

The receiver object has exactly `wire_version` (integer 1), `tenant_id` (UUID), `gateway_id` (UUID), `gateway_generation` (id128), `delivery_handle` (id128), `receiver_runtime_id` (UUID), `receiver_session_epoch` (epoch), `local_root` (id128), and `binding_digest` (sha256). The receiver computes or receives the digest of the exact pre-delivery binding associated with the authenticated request; it never waits for the final observer fact, batch or proof. Its authenticated principal must independently match the receiver enrollment and epoch. The digest is a binding claim, not authentication or a grant. `local_root` must resolve to a committed root fact in that same receiver scope.

## Enrollment and generation authority

These are proposed new narrowly scoped enrollment records, not existing SQL17/18/23 tables. A trusted operator provisioner, authenticated under a dedicated provisioning role, creates immutable tenant-scoped records using privileged fixed-purpose functions; no gateway or receiver may self-enroll or choose its own authority. Each enrollment is bounded by `not_before` and `not_after`, records a random server-issued 128-bit generation and has a prepaid append-only irrevocable closure/revocation record. A new gateway enrollment has a finite lifetime greater than zero and at most 24 hours. Receiver enrollment may never outlive its existing receiver session. Existing runtime session limits are preserved; no lifetime is extended or silently shortened. Provisioning checks exact tenant/source/collector/workload relationships using the existing source, workload-instance, lifecycle and credential records, and requires current operator authorization. Terminal records and identifier reservations cannot be removed in a way that permits identity or generation reuse.

A gateway enrollment contains `(tenant_id, gateway_id, gateway_generation, collector_id, source_id, gateway_observer_leaf_sha256, gateway_backend_client_leaf_sha256, not_before, not_after)`. The observer and backend leaves are separately provisioned and reserved for their own purpose, not shared with producer product/export or receiver credentials. The observer TLS principal is resolved by its actual peer leaf to exactly one currently live enrollment; its tenant, gateway ID/generation, collector and source must match the statement and source proof. The trusted gateway process receives an authenticated, locally installed enrollment snapshot bound to that generation, leaf, source and finite expiration, with monotonic freshness and revocation updates from the operator-controlled authority. The process fails evidence creation closed on missing, expired, stale or ambiguous state; it cannot extend the snapshot or use its contents as a self-issued grant. Provision a new generation for key rotation or replacement; the old generation's closure prevents further admission.

A receiver enrollment contains `(tenant_id, receiver_runtime_id, receiver_session_epoch, receiver_lifecycle_id, receiver_instance_id, backend_server_leaf_sha256, receiver_evidence_leaf_sha256, not_before, not_after)`. Provisioning binds the runtime/epoch to the existing causal runtime session and SQL18 instance/lifecycle, validates the backend server credential against that same workload identity, and reserves a separate receiver evidence client leaf. The gateway maps the actual verified backend server leaf to exactly this current enrollment, while the receiver verifies the dedicated enrolled gateway backend client leaf on the same connection. The receiver evidence endpoint maps its actual mTLS client leaf to that exact enrollment. Leaf uniqueness across purpose and live enrollments, bounded certificate validity, terminal events and operator-authorized rotation must be enforced under the same origin locking discipline as SQL17/18/23. A replaced receiver/epoch needs a new enrollment; no caller-supplied field substitutes for these checks.

The gateway's local snapshot and connection verification must fit the original deadline and require no synchronous database/remote lookup in the business callback. If current state or peer identity is unavailable, no binding is minted; ordinary forwarding remains independent. These are normative requirements for a future implementation, not claims that existing profile 503 already provides them.

## Global credential-purpose reservation: proposed SQL26

Migration 18 already creates the anonymous global `contour.causal_leaf_reservations` namespace, with `leaf_sha256` (exactly 32 bytes) as its primary key across all tenants and `leaf_class` restricted to `product` or `export`. FORCE RLS, owner-only policy, revoked raw privileges, immutable UPDATE/DELETE and no-TRUNCATE triggers protect it. Existing product credentials reserve through the `origin_credentials` BEFORE INSERT trigger under the origin tenant and credential gates; existing runtime enrollment reserves the export leaf in the same transaction as its binding. A primary-key conflict is mapped to a generic `23505` failure. An exact authorized retry of an already committed existing enrollment is recognized before a new reservation insert; a failed or rolled-back new transaction leaves no reservation. Committed reservations remain after revocation or closure. SQL18 backfilled product leaves while holding an exclusive lock on origin credentials; this proposed extension does not repeat or reinterpret that backfill.

A forward-only opt-in SQL26 must extend the CHECK on this **same table**, without altering its primary key, existing rows, FORCE RLS, owner policy, no-update/no-delete/no-truncate triggers, existing product trigger or export enrollment behavior. The allowed classes become exactly `product`, `export`, `gateway_observer`, `gateway_backend`, `receiver_backend`, and `receiver_evidence`. Existing product/export rows retain their original meaning; no profile 503 or legacy credential is reclassified. A separate purpose table plus cross-check is insufficient: only the single global unique constraint arbitrates concurrent cross-tenant and cross-purpose inserts atomically.

Only narrowly scoped SECURITY DEFINER functions owned by the established owner may insert the four new classes, using the origin prelude, tenant context, current operator-provisioner authorization, validated enrollment and actual credential fingerprint. Revoke direct table access and function execution from PUBLIC and all ordinary runtime/observer/receiver roles; grant only the dedicated authorized provisioning capability, never a raw INSERT or arbitrary class-selecting API. Each fixed-purpose function inserts its fixed class and matching enrollment and prepaid closure reservation in one transaction. Exact retry first checks the identical committed enrollment, its current authorization and its matching class; a different enrollment, changed data, revoked enrollment, wrong class or reused leaf returns a generic unavailable/conflict without revealing other tenants' reservations. Do not use `ON CONFLICT DO NOTHING` to turn a cross-purpose collision into success. Revocation, rotation or replacement never deletes, updates, relabels or frees a committed reservation. New credentials require distinct new fingerprints. Hash-lock collisions may serialize or cause a `40001` retry but never make two distinct fingerprints equivalent; the full bytea primary key, not the advisory hash, decides uniqueness. All transaction failures roll back both reservation and enrollment, quota charge and prepaid closure reservation; a later valid attempt may use a leaf whose earlier transaction did not commit.

Before activation, migration must verify the expected contiguous prior migration state and preserve all protected checks, roles and existing data; use transactional DDL and appropriate locks to prevent an unguarded gap while the CHECK is extended. It must assert all pre-existing rows remain byte-identical with their classes and all constraints, triggers, RLS and grants remain effective. No external credential trust or credential source is added by this schema change. New and legacy writers must contend on the same reservation primary key even across tenants; `23505` conflicts and `40001` lock contention remain fail-closed and retry only under fresh authority and the original deadline.

Required SQL tests cover every new class against product/export and each other in both commit orders; same-class identical authorized retry versus changed or cross-tenant enrollment; same fingerprint concurrent cross-tenant inserts with exactly one committed winner; distinct fingerprints with colliding advisory hash keys; revoked/closed/replaced identities retaining reservations; rollback after reservation but before enrollment and quota/closure failures; old product/export creation and old authorized retry unchanged; migration preservation of rows and permissions; and direct access, UPDATE, DELETE and TRUNCATE denied. Race tests must exercise actual concurrent transactions and both ordering directions; failures must not expose tenant identity, leave a partial enrollment or bypass the unique index. Confirm lock order and migration locks against all live writers in independent review before implementation.

## Admission, reconciliation and receipts

Authenticate first and derive principal and tenant from the authenticated session; reject mismatches and stale, expired, revoked or closed enrollment or authority. Gateway observer, receiver submitter, internal reconciler and existing scoped reader are distinct principal types with least-privilege functions; no PUBLIC execution, raw table grants or broader reader scopes. Admission does not extend existing grants, deadlines or stream lifetimes. Authority validity and committed origin proof must be verified rather than inferred from submitted fields.

The common delivery key is `(tenant_id, gateway_id, gateway_generation, delivery_handle)`. The observer replay record stores canonical fact digest under this key and rejects different content. Receiver admission atomically assigns that same key to the exact `(receiver_runtime_id, receiver_session_epoch, local_root, binding_digest)` across processes. This key does not include the receiver, so a handle cannot be reused for a different receiver, epoch, root or binding. Enforce corresponding uniqueness and exact field equality against the observer record. Only after rechecking all current sender, gateway, receiver, producer/session and relevant source authority may an exact retry return the original committed receipt; expired, revoked, closed or not-yet-resolvable authority returns no receipt and leaks no prior receipt or existence. If a receiver retry arrives before its observer, the server must resolve the required authority independently or return no receipt; it must not infer authorization from a stored assignment. Changed content conflicts after authorization. A lost acknowledgement or process restart cannot reopen assignment. Unknown write outcome is not a success receipt.

Producer attempt, receiver assignment and observer fact may arrive in any order, except that observer admission requires its committed V2 REQUEST and verified origin proof first. Persist a fact only after its sender, authority and quota checks pass; unresolved references do not grant authority. Reconciliation verifies the committed producer attempt, same marker and runtime scope, exact committed V2 REQUEST and verified origin proof, complete matching pre-delivery binding and digest, actual intended receiver assignment and receiver root, retry linkage, and all applicable admission-time authority. Under origin and generation locks, reconciliation additionally revalidates current producer session/grant, product credential and lifecycle, gateway enrollment/generation, receiver enrollment/session/credential, source and collector authority at the join time; any stale, expired, revoked or closed authority yields no new edge. Existing committed historical edges are retained without reinterpretation. It creates at most one immutable scoped edge for the specified assignment in one transaction. Unique constraints and conflict checks prevent duplicate or inconsistent edges. Pending historical facts do not bypass current join-time authority. A later revocation cannot erase a previously committed edge.

A proposed closed receipt has `wire_version: 1`, `kind: "observer" | "receiver"`, `fact_digest` (sha256), `receipt_id` (UUID), and `status: "stored" | "resolved"`. It is returned only after the matching durable commit. A byte-identical retry returns the original receipt bytes even if reconciliation later changes, but only after current-authority checks succeed; any status query requires separately authorized scope and must not disclose facts to unauthorized callers. Receipt semantics and transport principal mapping require review.

## Retention and failure evidence

A durable unique attempt assignment keyed `(tenant_id, producer_runtime_id, producer_session_epoch, producer_attempt_id)` maps to exactly `(gateway_id, gateway_generation, collector_id, record_id, marker_digest)` and is committed atomically with the first accepted observer fact. A fresh delivery handle does not permit that producer attempt to bind to a second frontend REQUEST or gateway generation. Additional backend deliveries are allowed only within the same assigned frontend request and a validated, acyclic predecessor chain. Concurrent races, crashes, lost acknowledgements and GC must preserve this constraint; inconsistent assignments fail closed.

Charge all facts, assignments, pending outboxes, edges, receipts, attempt reservations, generation-closure records and replay tombstones to the existing per-tenant 1,073,741,824-byte shared logical budget. For each new evidence record, charge its canonical payload bytes plus 256 logical bytes of fixed metadata; each separate receipt, assignment, attempt reservation, edge, outbox or tombstone charges its own canonical record bytes plus 256 bytes, once. Existing origin and causal records retain their existing accounting. Store exact per-record charges with the rows and update usage under the existing tenant quota lock in the same transaction; exact authorized retries incur no new charge. This is deterministic logical accounting, not a physical-size claim. Exhaustion creates no success receipt or partial edge and never evicts live proof.

Before enabling a new gateway or receiver enrollment, its provisioning transaction must reserve and charge exactly 1024 logical bytes for its permanent closure identity, in addition to the enrollment charge. Before any evidence can reference an existing producer runtime epoch, an evidence-activation transaction must similarly reserve and charge 1024 bytes for that epoch's permanent closure identity; this does not change the existing session issuance protocol. A reservation is keyed by tenant, namespace and exact generation or runtime/epoch and is idempotent.

The immutable closure body is canonical UTF-8 sorted-key JSON of a closed object with exactly `wire_version` (integer 1), `kind` (`gateway`, `producer`, or `receiver`), `tenant_id` (UUID), `gateway_id` (UUID for gateway, otherwise null), `gateway_generation` (id128 for gateway, otherwise null), `runtime_id` (UUID for producer or receiver, otherwise null), `session_epoch` (canonical decimal epoch string for producer or receiver, otherwise null), `effective_at` (finite UTC timestamp in exact `YYYY-MM-DDTHH:MM:SS.ffffffZ` form), and `reason` (`expired` or `operator_revoked`). Fields are all required, duplicates/unknowns rejected and kind-specific nullability enforced. Validate the canonical body is at most 768 bytes; its representation and all fields must be checked before activation and again before closure. An invalid or unrepresentable record fails closed and preserves the reservation and tombstones. Closure converts its existing 1024-byte reservation into the permanent charged record without increasing quota usage; the 1024 charge includes at least 256 bytes metadata and any unused padding, is never double-charged, and is never released. There is no new logical quota allocation when full. Failure to write or confirm closure means no associated replay tombstone may be removed. Reserved space cannot be spent by another item. Provisioning or evidence activation fails closed if its reservation cannot be funded; permanent identities are finite under the shared budget, so eventual exhaustion is possible and requires an explicit future capacity policy, not silent eviction or an assumption of infinite storage.

Every new provisioning, admission, reconciliation and GC function uses one origin prelude in a read-committed, single-tenant transaction. First `begin_origin_operation` refuses any preheld advisory locks and acquires the tenant's exclusive try-advisory gate; a failed try returns SQLSTATE `40001`. Gather all required actual peer/purpose credential leaves from bounded candidates, deduplicate and sort by their actual signed credential advisory hash keys as SQL23 does, then take those credential gates. Next deduplicate and sort actual `collector_lock_key` values, including producer and receiver collectors where applicable, and take all collector gates. Re-read and validate all candidate identities after those locks. Lock `origin_tenant_state` clock-floor row before `origin_logical_usage` quota row, matching the order observed in SQL17 proof completion; SQL23 takes the quota row but does not take a clock-floor row. The existing tenant gate serializes compliant same-tenant old and new writers. Then acquire new enrollment rows in fixed table-kind order `gateway`, `receiver`, `producer` and primary-key order within kind, followed by attempt assignments, delivery assignments, and facts, each in primary-key order. Do not acquire origin credential or collector gates after a new-row lock. New functions do not call another public origin operation that repeats the no-preheld-lock prelude: factor any needed work into private helpers that require the held gates. A failed try or changed candidate fails the transaction; an external caller may retry within the original monotonic deadline, without internal busy-waiting or extending it. Cross-tenant operations are prohibited. The extension of collector and new-row ordering is proposed, not a claim that old SQL already implements it; trigger paths, hash collisions and all writers require independent lock-order and concurrency review before implementation.

After the relevant locks are held, read `clock_timestamp()` as `initial_at` and require finite time no earlier than the existing `origin_tenant_state.clock_floor` and the relevant lifecycle/session history high-water marks. Do not use transaction-start time. Carry out admission, accounting and tentative inserts; immediately before the function returns, read a fresh `clock_timestamp()` as `final_at` and require it to be finite, no earlier than `initial_at`, the persisted tenant clock floor, or relevant history and acceptance times. Recheck current credential, session, grant, policy, enrollment, generation and each applicable cutoff at `final_at`, as SQL23 does; failure raises and rolls back all tentative changes. Advance the persisted tenant clock guard under the tenant gate as part of the successful transaction, so a later backwards wall-clock step is refused. Treat `final_at` as the database authorization linearization point before function return and commit, not a claim that commit takes zero time or that authorization remains current indefinitely afterward. The service must continue using its original monotonic end-to-end deadline and wait for successful commit before returning a receipt; an expired deadline or unknown commit outcome never yields a success receipt. A retry is reauthenticated and rechecked under current authority.

Each unresolved payload has an immutable server-derived first `accepted_at`; it becomes ineligible for resolution at `accepted_at + 24 hours`. A retry never resets that cutoff, and a later fact cannot extend an earlier fact's cutoff. Retain a resolved edge and its associated payloads through `resolved_at + 30 days`, where `resolved_at` is the final successful edge authorization time; reads and retries do not reset it. The final clock and cutoff checks run just before return, and actual commit remains subject to the original service deadline. After the applicable payload retention period, GC may delete payload bytes and decrement their exact stored charges, but must retain a charged minimal handle/attempt tombstone while any relevant authority is still open.

GC may convert prepaid reservations to permanent closure records only after all relevant gateway, producer and receiver authority has naturally expired or an operator explicitly revokes it. It must not silently revoke or forcibly close a still-valid shared generation to collect one fact, since other work may use it. Under the same origin and quota discipline it confirms that the exact gateway generation and all affected producer and receiver epochs are irrevocably closed, and only then may delete related replay/attempt tombstones whose payload retention has elapsed. The permanent closure identities remain charged and non-reusable. Any incomplete closure or uncertain outcome leaves tombstones in place. SQL19 currently caps `ttl_microseconds` and grant lifetime at 900,000,000 microseconds (15 minutes) and derives session expiration as the minimum of TTL, grant and policy expiration; its `queue_ttl_seconds` limit is 86,400 seconds. Preserve those existing ceilings and independent queue semantics; do not infer that every other authority or a future profile has the same lifetime. If any relevant authority has not naturally expired or been explicitly revoked, retain the charged tombstone until closure is safe. Never reopen consumed handles or attempt assignments, extend acceptance windows, or discard live proof to save quota.

Required negative tests include missing facts, wrong attempt/marker/request/proof, valid signed marker paired with wrong peer leaf or lifecycle, a reused producer attempt with a fresh handle and a different request, response substitution, swapped handles across concurrent requests, wrong tenant/gateway/receiver/epoch, HTTP/2 interleaving, backend retries to another instance, conflicting roots across receiver processes, duplicate and lost-ACK retries, restart, stale or revoked credentials, all allowed fact arrival orders with observer-before-proof rejected and retried only under current authority, delayed arrivals beyond unresolved expiry, quota failure during assignment, and replay after cleanup. Each must produce no false or additional edge. Positive tests require one exact three-fact edge, correct fan-out and retry separation, scoped receipts, original forwarding and latency limits, real TLS and receiver integration, and rendered graph evidence. A unit codec, mock or build alone cannot prove those runtime properties.

Review must verify the proposed enrollment implementation, origin lock order, source and signed-marker extraction, fail-closed current-authority checks, collision-free global uniqueness, charged closure retention, canonical vectors and all stated timing/GC rules against existing security boundaries. The protocol and new records remain proposed. This document does not authorize or implement SQL, endpoints, new grants, a receiver runtime or a codec.

## Wire codec review status

The data-only wire codec and shared canonical vectors do not implement or authorize admission, signature verification, enrollment, reconciliation, retention, or cleanup. Authority timing, revocation and lock ordering, expiration and irreversible generation closure, quota accounting, and garbage-collection safety remain blockers for implementing those boundaries and require independent review and runtime evidence.

## Gateway provisioning interface choice

The gateway-only SQL26 slice records a trusted operator/issuer assertion; it does not verify a policy signature, certificate possession, receiver enrollment, or a causal edge. As in SQL19, a future caller must independently verify the complete signed policy and source scope before constructing the privileged claim, round issued time upward and expiry downward to exact microseconds, and retain the original monotonic service deadline. SQL must compare the exact stored policy envelope and current revision plus the independent gateway source mapping and initial/final validity checks; a current revision alone is insufficient. A separate fixed-purpose admin-owned gateway predicate uses technique gateway; existing runtime predicates remain unchanged.

The closed trusted claim has tenant, gateway, collector, source, project, service, environment, deployment and source-instance UUIDs; a non-bearer 32-byte provisioning nonce; distinct 32-byte observer and backend client leaf digests; exact u64 policy revision, bounded policy envelope, verified finite policy issued/expiry times, and TTL in1..86,400,000,000 microseconds. A purpose-specific NOLOGIN provisioner has EXECUTE only and no automatic role membership or raw access. Server-created generation and times are returned only after durable commit; exact authorized nonce replay returns the original claim/generation/lease without extension. New authority, policy, quota and scope checks precede nonce lookup, while changed contents conflict. Rotation requires the previous generation to be closed or expired and permanently new leaves.

Closure is a separate privileged revocation or expiry operation under the same provisioner role and origin/floor/quota locks. It cannot mint evidence or revive authority, so it must not require an expired original policy to become current again. Expiry closure requires a safe clock at or after enrollment expiry; explicit operator revocation may close a live enrollment. Conversion consumes only the prepaid terminal slot and retains its permanent charge. Receiver enrollment remains unexposed until a separately qualified receiver profile and APIContour-issued certificate/deployment binding are implemented and proven.
