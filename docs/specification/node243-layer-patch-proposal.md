# Review proposal: narrow Node 24.22.3 image layer

Status: preparation reviewed, 2026-11-12. Root selected owned isolated qualification of this bounded existing-component security update under the owner's MVP/Guardrails maintenance authority. No image has yet been built, activated, published, or accepted. The [proposed Dockerfile](../../deploy/pilot/node-red-node243.Dockerfile) is not referenced by an existing profile or build. The bounded qualification decision and source review are recorded in the orchestration task; profile activation still requires the actual evidence below. This is not a build-ready or security acceptance claim.

The candidate derives a **new immutable image** from the existing Node-RED 5.0.9 image and copies only `/usr/local/bin/node` from the official Node 24.22.3 Alpine image; it changes `NODE_VERSION` to `24.22.3` so metadata does not retain the old version. It executes no `RUN`, APK, npm, SSH scan, installation or dependency resolution. The final base retains its `node-red` user, application and dependency tree, operating system, entrypoint, healthcheck, other environment, tools, volumes and flow behavior as inherited metadata and filesystem, subject to actual comparison and runtime proof. A copied executable can still change behavior, permissions and compatibility; these are not established by source inspection. This does not change a running image or reinterpret existing profile 503. It avoids a newly resolved package closure, but introduces an APIContour-maintained composite image, builder and update responsibility; Root limited this maintenance responsibility to the existing component patch and owned qualification; a broader package or deployment change requires a separate decision.

[Node's 24.22.3 release](https://nodejs.org/en/blog/release/v24.22.3) identifies it as a security release, including TLS and HTTP/2 fixes. Copying a Node executable alone does not establish that every affected dependency is patched: inherited OS, npm, application packages and external libraries retain their own versions and vulnerabilities. Investigate dynamic linking and exact component versions. The existing upstream [healthcheck](https://github.com/node-red/node-red-docker/blob/9e8ee9b7670bc956de928fe1b379090ffbc113c7/.docker/healthcheck.js) has a subprocess using `NODE_TLS_REJECT_UNAUTHORIZED=0`; preserving this existing behavior is not permission to apply that policy to business traffic or broaden its use, and it requires separate review.

The tags provide context; the Dockerfile uses immutable index digests. Verify official publisher provenance, re-fetch and hash the selected per-platform manifests, configs and every layer before use. Hash the exact extracted executable per architecture and compare it with independently verified official release/build artifacts, documenting the Alpine/musl build provenance; the standard Node release checksum alone may not identify the Alpine image's executable. [Official Node image source](https://github.com/nodejs/docker-node) and [Node release](https://nodejs.org/en/blog/release/v24.22.3) are primary starting points, not proof of the downloaded binary's provenance.

## Acceptance evidence required before any activation

- Inspect both executables and final images on amd64 and arm64: hash, ELF interpreter, dynamic libraries, musl and `libstdc++` ABI, loader resolution, file owner/mode, Node and Node-RED versions and dependency versions. Exercise the inherited native bcrypt module and other native addons under the final executable. A compatible Node major does not prove ABI or musl compatibility.
- Compare image config and filesystem against the immutable base, accounting only for the intended Node binary and version environment change; verify `node-red` user, tools, entrypoint, healthcheck, flows, permissions, process shutdown and startup behavior. Review residual OS/npm and healthcheck risks separately.
- Run owned per-architecture tests for Node-RED and flows, actual TLS identity and permitted session resumption, crypto, native bcrypt, factory/exporter and inbox paths, privacy, resource and performance limits, and all mandatory protected checks. Test failure, cancellation, revocation, expiry, and wrong image/profile/credential cases. Preserve existing deadlines and trust checks.
- Allocate and independently review a new, exact immutable candidate profile 504, including its actual migration, ledger, image digests and enrollment, only through the authorized process. No profile 503 mutation, broader allowlist, external registry publication, deployment, or customer credential use is authorized by this proposal. No build or activation is authorized merely by this document.
